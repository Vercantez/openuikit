# darwin/loader-exports.txt -- symbols provided by THE LOADER, not by a dylib.
#
# On Darwin these live in /usr/lib/system/libdyld.dylib, which Apple's
# libSystem.B.tbd re-exports (its file names 39 such libraries). Here there is
# no libdyld.dylib, because the loader IS dyld: build/machorun, a Linux ELF PIE,
# defines them and binds them into the guest.
#
# scripts/gen_tbd.sh merges the non-internal names below into libSystem.B.tbd,
# because a guest linking -lSystem must be able to resolve them. It also refuses
# to let this file rot -- see the three checks in that script's header:
#   * every name here must really be defined by build/machorun
#   * this list must be exactly the set our dylibs import and none of our
#     dylibs export, minus the _glibc_* flat-bind boundary
#
# Names are MACH-O names: C `foo` is `_foo`, so the loader's ELF symbol is the
# name here with one leading underscore removed. Two annotations override that:
#
#   =<elf-name>   the loader satisfies this Mach-O name under a DIFFERENT ELF
#                 name. Only dyld_stub_binder needs it: src/resolve.c special-
#                 cases that name and binds it to mr_stub_binder_trap, which
#                 aborts -- machorun binds the classic lazy stream eagerly, so
#                 reaching the binder is a loader bug, and the trap is how that
#                 "never" stays checkable. There is no symbol literally called
#                 dyld_stub_binder anywhere, which is correct and is exactly the
#                 kind of thing CHECK 1 exists to force someone to write down.
#
# `#internal` marks a symbol the loader really does export but that the SDK
# does NOT advertise to guests: it is a seam between the loader and our own
# dylibs, not API. It is still checked for existence.

# --- objc4's -delay_init references to the Swift runtime (src/resolve.c) ----
#
# ld64.lld-18 does not implement -delay_init, so objc4's swift_retain and
# swift_release come out as ordinary flat-lookup binds that must resolve at
# load time even when there is no Swift runtime. The loader defines them as
# diagnostic traps, and the loader is the LAST place consulted -- every loaded
# image is searched first -- so a real libswiftCore.dylib always wins whatever
# order the guest linked its dylibs in. They used to live in libSystem.B.dylib,
# where they won that lookup instead, which is what made `-lswiftCore` before
# `-lSystem` load-bearing on a Swift guest's link line.
#
# #internal is deliberate here and load-bearing in its own right: these must
# NOT be merged into libSystem.B.tbd. A guest that linked against that promise
# would get an undefined symbol at run time, because the loader satisfies them
# only for our own dylibs (the is_runtime host-lookup path in src/resolve.c),
# never for a guest.
_swift_retain       #internal
_swift_release      #internal
