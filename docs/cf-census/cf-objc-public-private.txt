# CF's Objective-C surface, split by whether Apple documents it
#
# Of the 151 selectors CoreFoundation messages (docs/cf-census/cf-objc-methods.txt),
# 86 appear in Apple's public Foundation headers and 65 do not.
#
# This split decides HOW each signature gets reconstructed, and the two halves
# have different and complementary sources of truth:
#
#   PUBLIC (86) -- documented API. We write the declaration clean-room and
#   VERIFY it against Apple's real header with scripts/verify_sigs.py. Apple's
#   headers are a reference to check against, never a source to copy: this
#   project's clean-room standard is stated in ~/swiftcore-macho/sdk/foundation/
#   Foundation.h and there is no reason to weaken it here.
#
#   PRIVATE / SPI (65) -- Apple-internal, absent from every public header,
#   so there is no reference to verify against. But these are BETTER determined,
#   not worse: CoreFoundation is the CALLER, and its call sites pass typed
#   arguments and consume typed returns. CF_OBJC_FUNCDISPATCHV carries the return
#   type as a macro argument. So for the private half the signature is derivable
#   from the code that uses it, which is a stronger source than a header would be.
#
# A wrong ObjC signature is the posix_spawnattr_t hazard moved from C to
# Objective-C: the message compiles, the selector matches, and the argument or
# return register is wrong. Neither half may be guessed.
